## 3. 模型：采集器定义 → 运行配置 → 任务实例

用户描述的「一个脚本有多个配置点」，建议称为 **采集器及运行配置**。

### 采集器定义

由开发者在模块里声明，说明实现能力：

- 站点、用途及支持的搜索/URL/详情等任务类型。
- 采集方式和阶段：HTTP、Selenium，或多阶段混合。
- 登录要求：无需登录、可选登录、必须登录（当前实现只有无需/必须两类）。
- 接受的凭据类型，如 Cookie、Token 或 API Key；后两类为后续扩展能力。
- 输入参数、输出字段、归一化规则和取消检查点。

HTTP 或 Selenium 不决定是否需要账号：公开接口可匿名，HTTP 接口也可能需要 Token；
浏览器可以匿名，也可以需要 Cookie。采集方式与身份要求是独立维度。

当前 META 的 needs_account / account_site 仍控制运行；本轮新增 collection /
authentication 只描述真实能力并提供界面分类。迁移时必须保持新旧声明一致。

### 运行配置（可保存模板，待实现）

每个采集器可以保存多份配置，例如「淘宝日常搜索」「淘宝详情补采」。配置分区如下：

| 分区 | 配置点 |
|---|---|
| 采集目标 | 关键词、URL、页数、详情范围、筛选条件 |
| 执行方式 | 仅显示该模块真正支持的路线与阶段；浏览器参数等高级设置折叠 |
| 登录与账号 | 兼容账号池、自动选号/指定账号、会话保持、失败后的换号策略 |
| 可靠性 | 请求间隔、超时、重试次数、任务并发与取消行为 |
| 数据输出 | 受允许的数据目标、归一化映射、去重规则、原始字段保留与导出 |

原始脚本的搜索、URL 和详情模式需要分别核对能力，再接成可配置任务；
不把同站点所有脚本无差别当作一个功能。当前统一库的 NORMALIZERS 对站点写死，
后续应把输出映射移到采集器声明中，才能真正做到新增采集器不改内核。

默认值来自采集器；运行配置保存用户选择；任务可覆盖允许调整的参数。
池和账号的配额、并发上限是约束，不能通过任务参数放大。

### 任务实例

运行时冻结有效配置，记录采集器版本/配置版本、池 ID、实际账号 ID、执行阶段和数据目标。
记录不包含明文凭据。工作流步骤引用运行配置，也允许保存步骤参数覆盖值。
随后编辑模板不改变已经运行或完成的任务。

## 4. 多账号池及脚本绑定（已实现，独立配置模板待做）

采用命名逻辑池，按站点和用途组织，例如「淘宝日常采集」「淘宝详情采集」。
采集方式作为兼容能力筛选，不强制把同一登录身份拆成 Selenium 账号和 HTTP 账号。
Cookie 是否能复用到 HTTP 客户端，由该站点适配器验证，不能假设所有站点都支持。

关系：

- 一个池可供多个兼容采集器使用。
- 一个采集器可有多份运行配置，每份配置绑定一个默认池。
- 一个账号可加入多个兼容池，但身份、配额、登录状态和并发占用始终按同一个账号 ID 计算。
- 当前首期采用一个任务保持一个账号；不在浏览器任务中每个请求换账号。

用户不需要逐个修改脚本文件来绑定账号。界面根据站点和凭据类型列出兼容池；
只有一个兼容池时可作为默认项，有多个时选择并保存一次，以后直接运行配置。
无兼容池时引导创建池和录入账号；跨站点绑定或错误凭据类型应在保存时拒绝。

账号池管理界面至少包含：创建/重命名/停用池、维护成员、查看绑定的运行配置、
设置默认池和轮换策略、账号授权/更新、登录状态/额度/占用情况及使用历史。
当前界面已支持命名池设置、成员复用/移出、网页登录录入、手机号与名称管理、批量 Cookie JSON 导入、同身份更新、状态、额度、占用和历史。
采集页显式选池；工作流每步独立选池并可仅保存。查看独立配置模板绑定关系、批量扫码授权队列仍待做。

## 5. 批量扫码录入流程（待实现）

2026-10-18 第一种登录方式已实现：填写管理手机号（名称默认该号码，可自定义）→ 打开独立官方登录页面 →
用户自行扫码/手机登录 → 服务端检测核心登录 Cookie → 加密保存到所选池 → 继续添加下一个账号。
只进行 Cookie 捕获时不标记登录有效；已有账号的重新登录须核对相同平台身份。
手机号通常无法完整自动获取，必须由用户填写，掩码不能推测还原。显示名与手机号、平台用户身份分别管理。
打开/等待/保存/失败/取消/超时可见，单次 10 分钟，关闭网页不取消已打开的授权任务。
当前没有一次添加多个手机号后自动排队的批量流程；以下是后续设计。

用户选择池和站点适配器 → 新建多个账号录入槽位 → 系统排队展示登录窗口/二维码 →
用户用对应账号扫码 → 适配器确认登录成功及实际账号身份 → 加密保存 → 自动进入下一项。

每个账号首次授权通常需要分别完成扫码。系统减少的是打开窗口、复制 Cookie、
运行导入脚本和分配池等手工步骤，不能替用户完成手机授权，也不能保证永不过期。

- 每个账号使用独立浏览器会话，避免上一账号登录态串到下一项。
- 等待、成功、超时、跳过、失败可见；失败可以单项重试，不重做整批。
- 新增时识别重复账号；更新凭据时确认实际身份，不能把另一个账号覆盖到原账号上。
- 已录入且有效的凭据由采集任务复用，不要求每次采集重新扫码。
- 不支持扫码的站点提供该站点支持的授权/Token 导入方式，不显示无效扫码入口。
- 按用户现有要求，本轮不启动淘宝登录，不恢复已知过期凭据。

## 6. 选号、状态和并发

旧 take(site) 仅保留给兼容调用和模块自测；其计数不构成独占租约。
生产 TaskRunner 已使用 lease_account(site,pool_id,task_id)，按池成员、健康、登录标记、额度及占用选号，
一个任务内重复取号返回同一账号。90 秒租约、25 秒续约，结束清理后释放，跨池共享身份也不能绕过占用。
停用/过期/空池不回退其他池。采集器 exclusive 约束仍保留，因此某些采集器全局只允许一个实例。

当前选号顺序：兼容站点/Cookie 凭据 → 登录标记不为过期 → 未冷却且额度足够 →
可取得账号租约 → 按最少使用或最久未使用策略选择。指定账号策略待实现。

- 首期账号默认并发上限 1；取得租约后才使用，完成/失败/取消时释放。
- 租约带心跳和到期时间，进程异常后可回收；多池引用同一账号也不能绕过占用限制。
- 浏览器任务保持同一账号和会话。需要换号时在安全检查点切换，并保存已完成位置。
- HTTP 会话也先采用任务内固定账号；后续按适配器能力支持按批次轮换。
- 账号失效与采集器/存储错误分开处理，不能因解析 bug 或入库失败惩罚账号。
- 无账号时按配置等待、停止或失败，给出原因，不无限重试或偷偷越池选择。

状态分为四个维度：轮换状态、登录状态、额度、运行占用。
healthy 只表示池内轮换状态；「有效」必须有检测结果和检测时间。
Cookie 自带时间戳只能用于本地过期提示，不能证明网站仍接受该登录态。
本轮淘宝的「过期待检测」是已知问题标记，不能推广成所有未来淘宝账号永久过期。
